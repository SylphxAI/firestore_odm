# Model generation benchmark

From `packages/firestore_odm_builder`, run:

```sh
dart pub get
dart run benchmark/model_generation.dart /tmp/model-output
```

The benchmark resolves a model with 10, 100 or 1,000 numeric fields, each with
`@Min(0)` and a default value, plus a document ID. It then measures
`ModelBuilderGenerator.generate` after five warmup calls, recording eleven
calls per size as JSON lines. The optional directory receives generated source
for byte comparisons. Temporary fixtures and analyzer contexts are cleaned up.

This measures model generation after analyzer resolution. It excludes SDK
startup, dependency resolution, builder compilation and build_runner overhead.
RSS is the process reading after each size, including the analyzer; it is not
an isolated measure of generator memory. Timings have no CI threshold.

## Measured change

On 2026-10-30, baseline `a610f1cf` and the shared-analysis implementation ran
serially in alternating order, twice each, on the same shared Linux host with
Dart 3.12.2 and identical dependency locks. These are pooled medians of 22 calls
per size and implementation:

| Numeric fields | Before | After | Generated bytes |
| ---: | ---: | ---: | ---: |
| 10 | 7.07 ms | 5.97 ms | 12,458 |
| 100 | 24.91 ms | 20.74 ms | 104,798 |
| 1,000 | 243.98 ms | 117.06 ms | 1,050,698 |

The 1,000-field case was 2.08 times faster in this sample. Every generated byte
matched across all runs. Whole-process peak RSS was 747–750 MiB before and
746–747 MiB after; these samples do not establish a memory improvement. Small
case timings varied substantially. This is a synthetic scaling fixture, not a
measurement of application usage or end-to-end build speed.

[Raw samples and environment](model_generation_2026_10_30.json) include process
wall time and peak RSS for the complete benchmark invocation. Separately,
build_runner regenerated all 23 example model files without changing any of
their 349,549 bytes, and the generated API tests passed.
